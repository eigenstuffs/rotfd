# Preserved hierarchy candidates

These candidates are uncredited and are not linked into the matching-source build. Their private probes apply real relocations at recovered addresses; the reported differences are comparison evidence, not an acceptance claim. All original DOL bytes remain untouched.

- `scratch/game_hierarchy_remove/best21.cpp`: removal/coalescing routine at `0x801FC514..0x801FC998`, 1,156 emitted bytes. Twenty-one differing bytes remain, confined to register selection and initial owner-copy scheduling. Later list searches, layered typed-handle initialization, assignment, compaction, virtual unlink calls and return paths match. The observed empty typed handles perform seven and four zero stores through nested constructor layers. Their original class identities remain unknown.
- `scratch/game_hierarchy_append/near-match.cpp`: append routines at `0x801FC998..0x801FCCF4`, with exact emitted sizes of 420 and 440 bytes. Six bytes differ in the first routine, from the order of adjacent stack-address and identity-address instructions. Nine register bytes differ in the second routine's duplicate lookup. Ordinary list growth, allocator calls, entry construction, reference increments and virtual linking otherwise match. Search variants preserve constructor, inline-helper, manager-view and loop-shape experiments.
- `scratch/game_hierarchy_recovery/detach_const_reference.cpp`: updated removal/notification routine at `0x801FCCF4..0x801FCF20`, now exactly 556 emitted bytes and ten relocations. Ten differing bytes remain solely in search-loop register choices. A real by-value owned handle passed to `fn_801FC514` retains the temporary address through construction, reference adjustment, the call and destruction. A distinct `RelatedManagerView` restores the original second table load; a const input reference restores the zero/value-load/reference-adjustment sequence. All code after the search loop is exact. The earlier 548-byte source remains preserved under `scratch/game_hierarchy_detach`.
- `scratch/game_hierarchy_recovery/create_compare_value.cpp`: newly reconstructed resource-creation/attachment routine at `0x801FCF20..0x801FD3EC`, exactly 1,228 emitted bytes and 36 relocations. Only six bytes differ, from two adjacent address-setup instructions at `801FD300` and `801FD304`: the original prepares the local owner address before its identity source address, while the candidate reverses them. Every other instruction and temporary stack slot is exact. This is the same remaining owner-copy scheduling issue as the 420-byte append routine.

The probes use GC/1.3.2 with `-O4,p -inline deferred -use_lmw_stmw on`. Earlier compiler versions and several inline/optimization variations did not solve the remaining lifetime differences. These files are research evidence for further reconstruction; generated progress must continue to count the original assembly fallback for these addresses.

## Resource-creation ABI findings

The `801FCF20` routine obtains a resource from a global provider, initializes a new typed handle, selects its attachment target, compares resource identifiers, appends the result to the hierarchy, optionally links the hierarchy's identity, and returns the appended handle. Its early exits return the observed empty typed handle. Broader resource/class identities remain inferred.

`fn_80263308` consumes the incoming third argument in `r5`. Ghidra omits that argument at this particular call, but the callee and other callers retain it. A correctly declared returned derived handle plus that forwarded context preserves both the hidden-result ABI and the original `r8` global-base setup. The derived temporary's inline destructor calls the native handle destructor with flag zero. A four-byte name token passed by value into `fn_801FD4EC` recovers the exact final temporary slot and copy; an explicit pointer/local declaration produces different stack ordering.

Explicit `if/else` pointer resolution preserves the original null-result branches. The equivalent conditional expression incorrectly merges the new handle's initial zero with the null return in this context, omitting two original instructions. A distinct manager view retains the second resource-table access, and saving the first identifier value before comparison restores the observed operand order and register allocation. These source-level boundaries reproduce the original instructions without assembly or volatile changes.

The remaining six-byte boundary is preserved in `scratch/game_hierarchy_recovery/create_nearmatch_verification.txt`. Native scoped owner construction and a by-value virtual link conversion instead rematerialize the identity pointer and omit one instruction; placement construction adds an unwanted null guard. Bounded pointer/reference, const, constructor-return, accessor, helper and compiler-option probes are saved alongside the source. None of these near-matches is promoted or counted as matched source. The original protected DOL still verifies as `5da8295a79bf297ab62c620e6ac66210be1c6ef5`.
