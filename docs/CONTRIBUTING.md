# Contributing

The target is a C/C++ reconstruction of the `GSQE78` executable that produces
the SHA-1 recorded in [`build.sha1`](../config/GSQE78/build.sha1). Read
[`PROGRESS.md`](../PROGRESS.md) for measured status and the
[progress policy](PROGRESS_POLICY.md) before claiming a match.

## Build and choose work

Python 3.10 or newer and `ninja` must be on `PATH`. The build downloads pinned
decomp-toolkit, objdiff, binutils, CodeWarrior, and a supported compiler wrapper
when no explicit paths are provided. The existing workspace has working native
`tools/dtk`, `tools/objdiff-cli`, and `build/tools/wibo` on macOS arm64; those
paths are used in the verified commands below. On a new checkout, run
`python3 configure.py` without the local tool overrides so the helper can fetch
host-appropriate binaries. Hosts without a compatible WiBo build need Wine via
the `--wrapper` option. Inspect `python3 configure.py --help` for overrides.

Use the extraction and dependency instructions in the [README](../README.md).
From the repository root, build the standard configuration:

```sh
python3 configure.py --dtk tools/dtk --objdiff tools/objdiff-cli
ninja
ninja baseline
```

`ninja baseline` records a comparison point **before** editing. Keep it until the
change is finished; rerunning it replaces that comparison point.

Pick an item from the [roadmap](ROADMAP.md), check existing source and report
entries, and record the unit or symbol being worked on. Use a branch such as
`codex/match-moduleobject`. Work on one translation unit (TU), or one tightly
related group of functions, at a time.

## Match a translation unit

1. Locate its functions in [`symbols.txt`](../config/GSQE78/symbols.txt),
   generated `build/GSQE78/asm/`, and `decomp/all_functions.c`. Consult
   [`filemap.json`](../config/GSQE78/filemap.json) for source-string references.
   A filename reference is evidence of ownership, not proof of a TU boundary.
2. Recover section ranges and symbol sizes. Put confirmed ranges in
   [`splits.txt`](../config/GSQE78/splits.txt), including associated data, small
   data, constructors, destructors, and BSS where applicable. Preserve symbol
   visibility: static functions referenced by a type table need their owning
   data in the same unit.
3. Write source under `src/` and declarations under `include/`. Keep the
   observed function order and original identifiers when supported by evidence.
   Label uncertain fields by offset and record inferred names in research notes.
   Preserve the local source style, including K&R declarations in the embedded
   Python code when they affect matching.
4. Register new source as `Object(NonMatching, "path/to/file.c")` in
   [`configure.py`](../configure.py), using the appropriate library and compiler
   flags. This compiles it for comparison while retaining the original object
   in the matching executable. An unregistered source file earns no progress.
5. Open the repository in [objdiff](https://github.com/encounter/objdiff) and
   select the unit. `objdiff.json` is generated by configure; do not maintain it
   by hand. Iterate on code, types, flags, and data until the intended unit
   matches. Shared-header changes require checking all affected units.
6. Change the object to `Matching` only when the whole unit can be linked from
   source. Reconfigure and run the standard build below. A failed SHA check
   means the promotion is incomplete even if individual functions look right.

The local `tools/compile_probe.py` and `tools/version_probe.py` help investigate
CodeWarrior output. Their raw or masked instruction comparisons are diagnostic;
they do not replace relocation-aware object comparison and the final DOL check.
See [research notes](research-notes.md) for the compiler probes and Python ABI
findings already collected.

## Verify and hand off

```sh
python3 configure.py --dtk tools/dtk --objdiff tools/objdiff-cli
ninja
ninja changes
```

`ninja` compiles registered source, links the matching configuration, checks its
SHA-1, and regenerates progress. `ninja changes` compares the new objdiff report
with the saved baseline. Use `ninja changes_all` to include improvements, then
inspect any regression rather than assuming a successful command proves there
were none. Debug, experimental compiler, and `--non-matching` runs are useful
locally but cannot establish completion of the standard target.

When complete source units are consolidated into a native C++ group,
`ninja changes` uses the full baseline and current reports to verify unique
ownership coverage of every retired unit's sections and functions. This can
reconcile a unit-name removal while preserving genuine numeric regressions.
The formatter never changes either report or the saved baseline. Do not make
the baseline an automatic build dependency: snapshot it explicitly before
editing and retain it until acceptance. Ambiguous, partial or overlapping
migrations remain visible for investigation.

Before exporting progress, the build checks that every linked source data/BSS
split fits within its compiler-emitted section. Trailing linker alignment must
have separate original ownership even when objdiff reports a complete match.
`build/GSQE78/source_extents.json` records this check; run
`python3 tools/audit_source_extents.py` to diagnose a boundary failure.

A handoff or pull request should identify the unit and address range, explain
the observed behavior or ABI correction, record compiler/flag changes, and give
the build and regression results. Include updated generated progress when
source status changes. Preserve reference-source attribution and licenses.
Keep original disc data, generated assembly, compiler binaries, and local
debugging output out of source contributions.

The workflow follows Melee's [build and objdiff loop](https://github.com/doldecomp/melee#building)
and [contribution guidance](https://github.com/doldecomp/melee/blob/master/.github/CONTRIBUTING.md),
adapted to this game's current TU discovery and compiler constraints.
